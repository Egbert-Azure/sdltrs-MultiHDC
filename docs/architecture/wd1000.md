# WD1000/1010 controller emulation

`src/trs_hard.c` / `trs_hard.h` — the Western Digital WD1000/WD1010 hard-disk controller. This is the one backend of the three that **came from upstream**: it is Tim Mann's original xtrs code for the Radio Shack TRS-80 Model I/III/4/4P hard-disk controller, inherited essentially unchanged. This fork's contribution to it is the port relocation for the Genie IIIs and the move onto the shared image layer.

It is also the least exercised of the three here. Neither of the two verified Genie IIIs scenarios drives it — G-DOS 2.4 uses the Xebec, Holte's CP/M 3.0 uses the OMTI. It is documented because it is wired in, it is the only backend that reaches all four slots, and Kämpf's CP/M is understood to use it.

## What it emulates

A register-based WD1000/1010. There is no SASI bus and no phase machine: the guest writes cylinder, head, sector and count into distinct registers, then writes a command byte, then moves data through the data register while polling DRQ. That is the fundamental difference from `omti.md` and `xebec.md`.

Tim Mann's original header note still applies: the definitions were inferred from various drivers and sketchy documents rather than a real WD10xx data sheet.

## Port map and the Genie IIIs relocation

Native (Model I/III/4/4P):

| Port | Register |
|---|---|
| `0xC0` | Write-protect switches (read only) |
| `0xC1` | Control — software reset, device enable, wait enable |
| `0xC2`–`0xC7` | ID and CTC registers (Model II only, not used here) |
| `0xC8` | Data |
| `0xC9` | Precomp (write) / Error (read) |
| `0xCA` | Sector count |
| `0xCB` | Sector number |
| `0xCC` | Cylinder low |
| `0xCD` | Cylinder high |
| `0xCE` | SDH — size / drive / head |
| `0xCF` | Command (write) / Status (read) |

On the **Genie IIIs the register file lives at `0x50`–`0x57`**. `trs_io.c` maps it by adding `0x78` before calling into this backend:

```c
case 0x50: ... case 0x57:
  trs_hard_out(port + 0x78, value);   /* → 0xC8-0xCF */
```

That keeps `trs_hard.c` itself free of a second port map — the backend only ever sees the native addresses. The Model 4P variant does the same trick with `+ 0x80`. Note that the Genie IIIs range covers only the eight WD1010 registers; the Tandy-specific `0xC0`/`0xC1` pair is not relocated.

## SDH: sector size, drive and head in one register

The SDH register (`0xCE`) is what makes this controller's addressing different from the two SASI ones:

```text
essddhhh
 e   = 0 CRC, 1 ECC
 ss  = sector size: 00=256, 01=512, 10=1024, 11=128
 dd  = drive (2 bits → TRS_HARD_MAXDRIVES = 4)
 hhh = head
```

Two consequences:

- **Four drives.** The two-bit drive field is why `HARD_IMAGE_SLOTS` is 4 and why slots 2 and 3 are tagged `WD1000 only` in the GUI. The SASI controllers' 1-bit LUN reaches only units 0 and 1.
- **A live sector size.** The guest can change bytes-per-sector at runtime. This is why `hard_image_offset()` takes `secsize` as a parameter rather than reading it from the image — the OMTI is fixed at 512 and the Xebec at 256, but this one is whatever the SDH register last said.

## Status and error registers

Status (`0xCF` read):

| Bit | Name | Meaning |
|---|---|---|
| `0x80` | `BUSY` | |
| `0x40` | `READY` | Drive ready |
| `0x20` | `WRERR` | Write error |
| `0x10` | `SEEKDONE` | Seek complete |
| `0x08` | `DRQ` | Data request — the guest's polling bit during a transfer |
| `0x04` | `ECC` | Corrected ECC (reserved) |
| `0x02` | `CIP` | Command in progress; software reset required |
| `0x01` | `ERR` | Error; read `0xC9` for the code |

Error (`0xC9` read): `BBDERR 0x80`, `DATAERR 0x40`, `IDERR 0x20`, `NFERR 0x10`, `MCRERR 0x08`, `ABRTERR 0x04`, `TRK0ERR 0x02`, `MARKERR 0x01`. The idle status this emulation settles on is `READY | SEEKDONE`.

## Command set

The command register's top nibble selects the command (`TRS_HARD_CMDMASK 0xF0`); the low nibble carries flags.

| Command | Value | Notes |
|---|---|---|
| `RESTORE` | `0x1r` | Seek to cylinder 0. Low nibble is the step rate, ignored here |
| `READ SECTOR` | `0x2x` | One sector into the buffer, then DRQ. **Multi-sector flag not emulated** — a set `MULTI` bit is rejected with `ABRTERR` |
| `WRITE SECTOR` | `0x3x` | Same, in the other direction, same multi-sector restriction |
| `VERIFY` / `SCAN ID` | `0x40` | Bounds check and seek only |
| `FORMAT TRACK` | `0x50` | Writes `seccnt` sectors of zeroes. Does not build a skew table |
| `INIT` | `0x60` | **Not implemented** — logs `init command not implemented` and returns a clean status |
| `SEEK` | `0x7r` | Position only |

Timing is not modelled: step rates in the low nibble are parsed and discarded, and every command completes instantly.

## Write protection

`0xC0` is the only place any of the three backends reports write-protect state back to the guest as a register: one bit per drive, plus `WPSOME` (`0x02`) if any drive is protected. `INTRQ` (`0x01`) is not emulated. Reading this port opens every attached image to sample its flag.

Actual enforcement is the shared one — `hard_image_open()` opens a protected image read-only, so writes fail at `fwrite()`.

## Shared with the other backends

Everything below the protocol is common: `hard_slot[]`, the Reed header decode, and `hard_image_offset()`. `hard_open()` is a thin wrapper that passes this controller's assumptions (`TRS_HARD_SEC_PER_TRK` = 32, `TRS_HARD_MAXHEADS` = 8) into `hard_image_open()` and translates a failure into `NFERR`. See `controller-abstraction.md`.

`SECTORSIZE` here is 1024 — the sector buffer is sized for the largest the SDH register can select, not the size in use.

## Other users of this backend

`trs_hard_getfilename()` is the one per-backend getter still called from outside its own file: `trs_disk.c` writes it into a state dump, and `trs_imp_exp.c` opens the same image directly for the emulator-trap import/export path. That is a genuine coupling to the WD1000 specifically, not a slot-level operation, which is why it does not go through `hdctl.md`.

## Debugging

`-io 0xc` enables both flags — they are the same bits the OMTI backend uses, so an OMTI trace and a WD1000 trace come out together:

| Flag | Bit | Shows |
|---|---|---|
| `HARDDEBUG1` | `0x04` | Every port access, with the register name and the Z80 PC |
| `HARDDEBUG2` | `0x08` | Every command, with drive/head/cyl/secnum/seccnt, plus sector-buffer dumps |

Port names in the trace are printed by `hard_cmd()` in the form `c8:DATA`, `ce:SDH`, `cf:COMMAND/STATUS` — in native addresses, so a Genie IIIs trace shows `c8` where the guest actually wrote to `0x50`.
